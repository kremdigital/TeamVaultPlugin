# Manual test plan

Чек-лист сценариев, которые `pnpm test` не покрывает (Yjs round-trip
между двумя реальными Obsidian'ами, конфликт-модалки на живом сервере,
длительный оффлайн со свежими правками). Делать против развёрнутого
сервера Team Vault (`https://<ваш-сервер>`) и **отдельного тестового
проекта**: сценарии создают, правят и удаляют файлы, и всё это уходит на
сервер и ко всем участникам проекта.

Нужны два пустых тестовых вальта, дальше они называются `test-vault` и
`test-vault-2` (имена любые). `<вальт>` ниже — путь к корню вальта, то есть к
папке, которую открывает Obsidian.

Названия кнопок и настроек даны для русского интерфейса плагина, в скобках —
для английского. Язык плагина по умолчанию совпадает с языком Obsidian, его
можно сменить в «Поведение» → «Язык интерфейса» (Behavior → Interface
language), см. S13.

## Pre-flight

### 1. Build the plugin into the test vault

Из корня репозитория плагина:

```bash
CI=1 pnpm install --frozen-lockfile
mkdir -p "<вальт>/.obsidian/plugins/team-vault"
TEST_VAULT="<вальт>" pnpm build:vault
```

Папку плагина нужно создать заранее: сборка копирует файлы только в
существующую папку. Сборка читает `TEST_VAULT` только из окружения, `.env` не
подхватывает (см. `.env.example`).

Получишь:

```
<вальт>/.obsidian/plugins/team-vault/
  main.js
  manifest.json
  styles.css
```

Это ровно три файла релиза — то же, что ставит каталог Obsidian. Повторить
для `test-vault-2`.

### 2. Зависимостей рядом не нужно

С 0.3.0 у плагина **нет нативных модулей**: оплог — JSON (`state.json`),
chokidar забандлен в `main.js`. Три файла из шага 1 — это вся установка,
никаких `node_modules`, junction'ов и `@electron/rebuild`.

Если в папке плагина остались следы 0.2.x — `node_modules/`, `package.json`,
`state.db*` — их можно удалить: плагин их не читает.

> ⚠️ Не держи рядом вторую копию плагина (например, бэкап старой версии)
> внутри `.obsidian/plugins/`: у неё тот же `id`, и Obsidian может загрузить
> именно её. Бэкапы — только за пределами `plugins/`.

### 3. Server side

- API-ключ — из Settings → API Keys на сервере. Скопировать `osk_…`.
- Создать пустой тестовый проект (через web-UI).
- Запомнить project id (есть в URL).

### 4. Open Obsidian

Открыть `test-vault` в Obsidian. Включить **Settings → Community plugins
→ Team Vault**.

## Scenarios

Состояния status bar ниже названы как в README: `connecting` —
«Подключение…» (Connecting…), `syncing` — «Синхронизация…» (Syncing…),
`connected` — «Синхронизировано» (Synced), `offline` — «Нет соединения»
(Offline), `paused` — «Синхронизация на паузе» (Sync paused).

### S1 — First binding, push to empty project

1. Положить в `test-vault` пару `.md` файлов (`note.md`, `subdir/x.md`).
2. Settings → Team Vault → «Серверы» (Servers) → «Добавить сервер» (Add
   server) → имя, URL (`https://<ваш-сервер>`) и API-ключ → «Проверить»
   (Test) → ожидать «Подключено как <email>.» → «Сохранить» (Save).
3. «Хранилища» (Vaults) → «Привязать хранилище» (Add binding) → выбрать
   сервер и проект → «Привязать» (Bind). В окне нет выбора папки, есть
   пояснение, что синхронизируется всё хранилище.
4. Status bar должен пройти `connecting → syncing → connected`.
5. На сервере (web UI) проверить, что файлы появились с правильным
   путём + содержимым.

### S2 — Pull empty vault from project with content

1. На сервере залить пару файлов через web-UI или `pnpm cli push`.
2. Открыть **второй** vault (`test-vault-2`), включить плагин.
3. Добавить сервер и привязать хранилище к тому же проекту (вальт пустой).
4. После `connected` файлы должны появиться в vault'е автоматически.
5. Кнопка «Привязать хранилище» теперь неактивна, под ней пояснение про одну
   привязку. «Удалить привязку» → кнопка снова активна. (Старая привязка к
   подпапке, если есть, показывается как «сервер · папка».)

### S3 — Two-device editing of one note (text)

1. Открыть один и тот же `.md` файл в двух Obsidian'ах (S1 + S2 vault).
2. Править разные места файла на обоих устройствах с паузами в пару
   секунд — правка уходит, когда Obsidian сохраняет заметку.
3. Через несколько секунд (сохранение ≈2 с + дебаунс 0.5 с + снапшот
   0.5 с) обе стороны и веб-UI показывают один итоговый текст: ни одна
   правка не пропала и не задвоилась.
4. Проверить что нет конфликт-модалок (текст идёт через CRDT).
5. Регрессия 0.3.2 — сохранить правку на S2, затем сразу править ту же
   заметку на S1. Правка S1 должна появиться на S2 и **остаться**: до
   0.3.2 она удалялась на S2, и удаление уезжало на сервер и обратно на S1.
6. Регрессия 0.3.2 — заметка, которую S2 не трогал с момента подключения
   (catch-up её пропустил, потому что диск совпадал с сервером): правка с
   S1 должна дойти до диска S2 без переподключения.

> **Ограничение:** синхронизация идёт по сохранению файла
> (`vault.on('modify')`), а не посимвольно — привязки редактора нет. Если
> правка приходит, пока в заметке есть несохранённый набор, Obsidian сам
> вливает набор в пришедший текст и показывает уведомление «modified
> externally, merging changes automatically»; при правке одних и тех же
> слов часть несохранённого набора может потеряться. Живое совместное
> редактирование — в веб-редакторе сервера.

### S4 — Offline edit → reconnect drain

1. Подключение работает. Сделать небольшое изменение в файле, дождаться
   синка (`connected` → `connected`).
2. Отключить интернет (Wi-Fi off или закрыть socket в DevTools).
3. Status bar → `offline`.
4. Сделать 5–10 правок (modify, delete, rename) — операции должны
   копиться в очереди оплога: массив `bindings.<id привязки>.pending` в
   `<вальт>/.obsidian/plugins/team-vault/state.json` (очередь сохраняется
   на диск сразу; можно оставить как black-box).
5. Включить интернет.
6. Status bar → `connecting → syncing → connected`. На сервере все
   операции применились.

### S5 — External agent edit (вне Obsidian)

1. Со включённым плагином и активным синком: в терминале, из корня
   `test-vault` (на Windows — Git Bash, не PowerShell: в Windows PowerShell
   5.1 `>>` пишет UTF-16LE, и в заметку попадают NUL-байты):
   ```bash
   cd "<вальт>"
   echo "external addition" >> note.md
   ```
2. Chokidar должен поймать modify (с дебаунсом 1s).
3. На сервере (или в S2 vault) изменения должны появиться.
4. Дополнительно: создать новый файл через CLI (там же, в корне вальта):
   ```bash
   echo "fresh" > from-shell.md
   ```

### S6 — Binary conflict modal

1. В оба vault'а залить одинаковый PNG (через S1 push).
2. На S1: отключиться (тот же приём, что в S4) и заменить PNG другим
   контентом (через шелл `cp other.png image.png` в папке вальта). Дождаться,
   пока операция встанет в очередь оплога (или статуса `offline`).
3. Параллельно на S2: заменить тот же PNG третьим вариантом.
4. На S1 включить интернет. Сервер пушит PNG версии S2 → плагин
   обнаруживает three-way conflict (storedHash != localHash != serverHash)
   и открывает модалку.
5. Проверить все три ветки: «Оставить серверную» (Keep server), «Оставить
   локальную» (Keep local), «Сохранить обе» (Keep both).
   - «Сохранить обе»: проверить, что появился `image.conflict-<ts>.png`.

### S7 — Delete-vs-update conflict

1. На S1 редактировать файл (есть несохранённые изменения).
2. На S2 удалить тот же файл.
3. На S1 — модалка delete-vs-update.
4. «Восстановить на сервере» (Restore on server) → файл переоткрывается на
   сервере, оба vault'а снова видят его.

### S8 — Long offline

1. На S1 отключить интернет.
2. Сделать 50+ правок (новый файл, модификация, удаление, пере­именование).
3. Подождать 1+ час (или просто перезапустить плагин через
   Settings → Community plugins → toggle).
4. Включить интернет.
5. Драйн очереди должен пройти за разумное время; status bar показывает
   `syncing` пока pending не дренаж­нётся.
6. Проверить что все правки применились на сервере.

### S9 — Status bar + commands

- Status bar реагирует на изменение state (отключи Wi-Fi, цвет/иконка
  меняется).
- Click → меню: «Синхронизировать сейчас» и «Приостановить» (на паузе —
  «Возобновить»), «История версий активного файла», «Открыть настройки».
- Палитра команд (`Ctrl/Cmd-P`; в скобках — названия при английском
  интерфейсе). У каждой команды ровно один префикс «Team Vault: »:
  - «Team Vault: Приостановить синхронизацию» (Pause sync) — status bar →
    `paused`.
  - «Team Vault: Возобновить синхронизацию» (Resume sync) — обратно.
  - «Team Vault: Синхронизировать сейчас» (Sync now) → notice «Синхронизация
    завершена».
  - «Team Vault: Переключить историю версий активного файла» (Toggle active
    file history) — открывает правую панель, повторный вызов закрывает.
  - «Team Vault: Открыть настройки» (Open settings) — фокус на вкладке
    настроек плагина.

### S10 — Log buttons

1. Открыть DevTools (`Ctrl+Shift+I`), вкладка Console. Settings → Team Vault
   → «Поведение» → «Уровень логирования»: «Отладка» (Behavior → Log level:
   Debug). Без перезагрузки плагина строки лога сразу появляются и в консоли.
2. Сделать пару правок.
3. «Открыть лог» (Open log) → открывается окно с содержимым `sync.log` и
   кнопками «Скопировать» (Copy) и «Очистить лог» (Clear log). В вальте новых
   файлов нет.
4. «Очистить лог» → notice «Лог очищен», повторное «Открыть лог» показывает
   почти пустой лог (только строки после очистки).
5. Вернуть «Информация» (Info): строки в консоли больше не появляются, тоже
   без перезагрузки.

### S11 — Stress test (1000+ files)

1. Создать в vault'е 1000 файлов (`for i in {1..1000}; do echo "f$i" > "f$i.md"; done`).
2. Bind → засечь время до `connected`.
3. Должно быть в разумных пределах (< 1 минуты на локалке).

### S12 — Подтверждение удаления, выгрузка плагина, окно истории

Правки 0.3.5 под линтер каталога, которые юнит-тесты проверяют только по
логике.

1. Settings → Team Vault → «Удалить» (Remove) у сервера: открывается окно
   Obsidian (не системный диалог) с заголовком, текстом и кнопками «Отмена» /
   «Удалить» (Cancel / Remove); фокус на «Удалить».
   - Escape, крестик, клик мимо окна, «Отмена» — сервер остаётся.
   - Enter или «Удалить» — сервер удалён, его привязки выключены.
   - Быстрый двойной щелчок по «Удалить» в настройках не открывает двух окон
     и ничего не удаляет: второй щелчок может прийтись на фон окна и закрыть
     его как «клик мимо» — это нормально. Двойной щелчок по «Удалить» внутри
     окна удаляет один раз.
2. То же для «Удалить привязку» (Remove binding): Enter удаляет, Escape —
   нет.
3. Command palette → «Переключить историю версий активного файла» (Toggle
   active file history) при открытой заметке: правая панель открывается и
   показывает историю; повторная команда её закрывает.
4. Settings → Community plugins → выключить Team Vault при активной
   синхронизации: в консоли DevTools нет ошибок, в `sync.log` есть
   `plugin unloading` и нет строк `unload: … failed`. Снова включить —
   синхронизация поднимается, правки, сделанные до выключения, на сервере.
   - Офлайн (сервер недоступен) изменить пару заметок, выключить плагин и
     сразу включить: очередь не потерялась — после возврата сети правки
     уходят на сервер. В `sync.log` нет `previous instance is still shutting
down` (он допустим, только если выгрузка заняла больше 5 секунд).
5. «Скопировать» в окне лога (S10) кладёт лог в буфер обмена.

### S13 — Язык интерфейса

Правка 0.3.5: настройка «Язык интерфейса» вместо жёсткого русского.

1. Новая установка (без `data.json`) при русском Obsidian: вкладка
   настроек, статус-бар и палитра команд — по-русски; в «Поведение» →
   «Язык интерфейса» выбрано «Как в Obsidian». У вальтов, где плагин стоял
   до 0.3.5, в `data.json` записано `"language": "ru"`, там выбран «Русский».
2. Выбрать «English»: вкладка сразу перерисовывается по-английски, текст в
   статус-баре — тоже. Палитра команд пока по-русски; выключить и включить
   плагин (Community plugins) → «Team Vault: Sync now».
3. Вернуть «Как в Obsidian», переключить сам Obsidian на английский
   (Settings → General → Language, перезапуск): плагин по-английски.
   Любой язык Obsidian, кроме русского (например, Deutsch), — тоже
   английский.
4. Переключателя «Синхронизация при запуске» больше нет. Вальт, чей
   `data.json` ещё содержит `syncOnStartup`, открывается без ошибок в
   консоли. Поле пропадает из `data.json` при первом же сохранении
   настроек — в том числе сразу после подключения к серверу, когда плагин
   записывает время синхронизации.

## When done

Заполнить чек-лист (галочки рядом с каждым S1-S13). Найденные баги
фиксить как issues или сразу патчить + добавлять regression-тесты в
`tests/`.

После прохода S1–S10, S12 и S13 (S11 — желательно, но не блокирует) можно
выпускать релиз по [RELEASING.md](./RELEASING.md): тег — ровно версия из
`manifest.json`, без `v` (`X.Y.Z`); тег `vX.Y.Z`, который оставляет
`pnpm version`, не пушить.
