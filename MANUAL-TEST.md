# Manual test plan

Чек-лист сценариев, которые `pnpm test` не покрывает (Yjs round-trip
между двумя реальными Obsidian'ами, конфликт-модалки на живом сервере,
длительный оффлайн со свежими правками). Делать против развёрнутого
сервера Team Vault (`https://<ваш-сервер>`) и **отдельного тестового
проекта**: сценарии создают, правят и удаляют файлы, и всё это уходит на
сервер и ко всем участникам проекта.

Нужны два пустых тестовых вальта, дальше они называются `test-vault` и
`test-vault-2` (имена любые). `<вальт>` ниже — путь к корню вальта, то есть к
папке, которую открывает Obsidian.

Названия кнопок и настроек даны для русского интерфейса плагина, в скобках —
для английского. Язык плагина по умолчанию совпадает с языком Obsidian, его
можно сменить в «Поведение» → «Язык интерфейса» (Behavior → Interface
language), см. S13.

## Pre-flight

### 1. Build the plugin into the test vault

Из корня репозитория плагина:

```bash
CI=1 pnpm install --frozen-lockfile
mkdir -p "<вальт>/.obsidian/plugins/team-vault"
TEST_VAULT="<вальт>" pnpm build:vault
```

Папку плагина нужно создать заранее: сборка копирует файлы только в
существующую папку. Сборка читает `TEST_VAULT` только из окружения, `.env` не
подхватывает (см. `.env.example`).

Получишь:

```
<вальт>/.obsidian/plugins/team-vault/
  main.js
  manifest.json
  styles.css
```

Это ровно три файла релиза — то же, что ставит каталог Obsidian. Повторить
для `test-vault-2`.

### 2. Зависимостей рядом не нужно

С 0.3.0 у плагина **нет нативных модулей**: оплог — JSON (`state.json`),
chokidar забандлен в `main.js`. Три файла из шага 1 — это вся установка,
никаких `node_modules`, junction'ов и `@electron/rebuild`.

Если в папке плагина остались следы 0.2.x — `node_modules/`, `package.json`,
`state.db*` — их можно удалить: плагин их не читает.

> ⚠️ Не держи рядом вторую копию плагина (например, бэкап старой версии)
> внутри `.obsidian/plugins/`: у неё тот же `id`, и Obsidian может загрузить
> именно её. Бэкапы — только за пределами `plugins/`.

### 3. Server side

- API-ключ — из Settings → API Keys на сервере. Скопировать `osk_…`.
- Создать пустой тестовый проект (через web-UI).
- Запомнить project id (есть в URL).

### 4. Open Obsidian

Открыть `test-vault` в Obsidian. Включить **Settings → Community plugins
→ Team Vault**.

## Scenarios

Состояния status bar ниже названы как в README: `connecting` —
«Подключение…» (Connecting…), `syncing` — «Синхронизация…» (Syncing…),
`connected` — «Синхронизировано» (Synced), `offline` — «Нет соединения»
(Offline), `paused` — «Синхронизация на паузе» (Sync paused).

### S1 — First binding, push to empty project

1. Положить в `test-vault` пару `.md` файлов (`note.md`, `subdir/x.md`).
2. Settings → Team Vault → «Серверы» (Servers) → «Добавить сервер» (Add
   server) → имя, URL (`https://<ваш-сервер>`) и API-ключ → «Проверить»
   (Test) → ожидать «Подключено как <email>.» → «Сохранить» (Save).
3. «Хранилища» (Vaults) → «Привязать хранилище» (Add binding) → выбрать
   сервер и проект → «Привязать» (Bind). В окне нет выбора папки, есть
   пояснение, что синхронизируется всё хранилище.
4. Status bar должен пройти `connecting → syncing → connected`.
5. На сервере (web UI) проверить, что файлы появились с правильным
   путём + содержимым.

### S2 — Pull empty vault from project with content

1. На сервере залить пару файлов через web-UI или `pnpm cli push`.
2. Открыть **второй** vault (`test-vault-2`), включить плагин.
3. Добавить сервер и привязать хранилище к тому же проекту (вальт пустой).
4. После `connected` файлы должны появиться в vault'е автоматически.
5. Кнопка «Привязать хранилище» теперь неактивна, под ней пояснение про одну
   привязку. «Удалить привязку» → кнопка снова активна. (Старая привязка к
   подпапке, если есть, показывается как «сервер · папка».)

### S3 — Two-device editing of one note (text)

1. Открыть один и тот же `.md` файл в двух Obsidian'ах (S1 + S2 vault).
2. Править разные места файла на обоих устройствах с паузами в пару
   секунд — правка уходит, когда Obsidian сохраняет заметку.
3. Через несколько секунд (сохранение ≈2 с + дебаунс 0.5 с + снапшот
   0.5 с) обе стороны и веб-UI показывают один итоговый текст: ни одна
   правка не пропала и не задвоилась.
4. Проверить что нет конфликт-модалок (текст идёт через CRDT).
5. Регрессия 0.3.2 — сохранить правку на S2, затем сразу править ту же
   заметку на S1. Правка S1 должна появиться на S2 и **остаться**: до
   0.3.2 она удалялась на S2, и удаление уезжало на сервер и обратно на S1.
6. Регрессия 0.3.2 — заметка, которую S2 не трогал с момента подключения
   (catch-up её пропустил, потому что диск совпадал с сервером): правка с
   S1 должна дойти до диска S2 без переподключения.

> **Ограничение:** синхронизация идёт по сохранению файла
> (`vault.on('modify')`), а не посимвольно — привязки редактора нет. Если
> правка приходит, пока в заметке есть несохранённый набор, Obsidian сам
> вливает набор в пришедший текст и показывает уведомление «modified
> externally, merging changes automatically»; при правке одних и тех же
> слов часть несохранённого набора может потеряться. Живое совместное
> редактирование — в веб-редакторе сервера.

### S4 — Offline edit → reconnect drain

1. Подключение работает. Сделать небольшое изменение в файле, дождаться
   синка (`connected` → `connected`).
2. Отключить интернет (Wi-Fi off или закрыть socket в DevTools).
3. Status bar → `offline`.
4. Сделать 5–10 правок (modify, delete, rename) — операции должны
   копиться в очереди оплога: массив `bindings.<id привязки>.pending` в
   `<вальт>/.obsidian/plugins/team-vault/state.json` (очередь сохраняется
   на диск сразу; можно оставить как black-box).
5. Включить интернет.
6. Status bar → `connecting → syncing → connected`. На сервере все
   операции применились.

### S4b — Старт без сети, цепочки переименований, эхо Obsidian

1. Закрыть Obsidian, отключить интернет, открыть вальт. Status bar не
   доходит до `connected`.
2. Удалить синхронизированную заметку `a.md`, переименовать `b.md` в
   `c.md`. В `state.json`: в `pending` — `DELETE` и `RENAME` с непустым
   `fileId`, в записях файлов нет `a.md` и `b.md`, есть `c.md`.
3. Там же переименовать `d.md` → `e.md` → `f.md`, затем `x.md` → `e.md`.
4. Включить интернет. После `connected`: `a.md` не вернулась, на сервере
   одна заметка `c.md` (не `b.md` и не копия), `d.md` на сервере одним
   переименованием стала `f.md`, `x.md` стала `e.md`; на диске нет
   `*.conflict-*` и `*.moving-*`. Каждое переименование в журнале операций
   сервера — один раз.
5. Pause sync, отключить интернет, Resume sync, повторить шаг 2 для других
   заметок — очередь та же, с `fileId`.
6. Во втором вальте (S2) переименовать заметку, меняя только регистр
   (`Note.md` → `note.md`). В S1 заметка переименована, в журнале операций
   сервера нет переименования в `Note.moving-<ts>.md`, в `sync.log` S1 нет
   исходящего `file:rename` для неё.
7. Одно имя с двух сторон: S1 офлайн переименовывает `a.md` (текст «A») в
   `c.md`, S2 тем временем переименовывает `d.md` (текст «D») в `c.md`. S1
   подключается: у всех `c.md` — заметка S2 с текстом «D»,
   `c.conflict-<clientId S1>.md` — заметка S1 с текстом «A». Других копий
   (`c.conflict-<ts>.md`) и дубликатов нет, тексты не поменялись местами.
   То же, если S2 не переименовывает, а создаёт новую `c.md`: она
   появляется на S1 сразу, её правки доходят. И если S1 офлайн не
   переименовывает, а создаёт свою `c.md`: у всех `c.md` — заметка S2,
   `c.conflict-<clientId S1>.md` — заметка S1, и следующие сохранения S1 не
   добавляют на сервер новых конфликтных копий. Затем второй раз: S2
   переименовывает свою `c.md`, S1 снова офлайн создаёт `c.md`, S2 тоже.
   После подключения S1: `c.conflict-<clientId S1>.md` не изменилась (текст
   первой заметки S1, без повторов), вторая заметка S1 —
   `c.conflict-<clientId S1>-2.md`, `c.md` — заметка S2. Так и с продом до
   исправления сервера (8a6d925): он сам всегда берёт первое конфликтное
   имя и затирает файл под ним, поэтому свободное имя выбирает S1.
8. Туда и обратно: S1 офлайн переименовывает `a.md` в `b.md` и обратно в
   `a.md`, S2 переименовывает `a.md` в `z.md`. S1 подключается: заметка у
   всех `z.md`, S1 ничего не отправляет.
9. Новая заметка, переименованная сразу: в S1 (онлайн, медленная сеть или
   Templater с `tp.file.rename`) Ctrl+N и сразу переименовать `Untitled.md`
   в `Meeting.md`. На сервере одна заметка `Meeting.md`, в журнале операций
   `CREATE Untitled.md`, затем `RENAME`; после перезапуска S1 `Untitled.md`
   не появляется. То же, если сеть обрывается до ответа сервера: после
   восстановления заметка переименовывается, второй заметки нет. И если
   сеть оборвалась до ответа сразу после Ctrl+N, а переименовали заметку
   уже без сети (или после Pause sync): после восстановления у всех одна
   `Meeting.md`. Так и тогда, когда до переименования в `Untitled.md` без
   сети дописали строку: у всех одна `Meeting.md` с этой строкой,
   `Untitled.md` нет ни на сервере, ни на диске S1.
10. Со старым сервером (без `clientId`): переименовать заметку `Draft` →
    `Plan` → `Plan v2`, затем в S2 вернуть ей имя `Plan`. S1 следует за
    переименованием S2.
11. Копия вальта с `data.json`: скопировать вальт S1 на другой компьютер
    вместе с `.obsidian`, открыть обе копии. Новая заметка, удаление и
    переименование в одной копии доходят до другой сразу, в `sync.log` —
    один `warn` «another device uses the same id». После `"clientId": ""` в
    `data.json` копии и перезапуска предупреждения нет.
12. Переименование во время подключения: S1 офлайн переименовывает `a.md`
    в `b.md`; включить интернет и, пока статус `syncing`, переименовать
    `b.md` в `c.md`. У всех `c.md`; после Pause sync и Resume sync — тоже,
    второй заметки нет.
13. Регистр имён (S1 — Windows или macOS, S2 — Linux, веб-редактор или
    MCP): в S2 создать `A.md` рядом с `a.md` (или переименовать в `A.md`
    другую заметку). На S1 `a.md` не меняется, `A.md` не появляется, на
    сервере тексты обеих заметок целы; после того как S1 переименует `a.md`,
    к нему приходит `A.md`. В S2 переименовать папку `Notes` в `notes`
    (только регистр): на S1 заметки остаются в папке, после перезапуска S1
    на сервере нет новых заметок, правка заметки из этой папки на S1 доходит
    до S2.

### S4c — Заметку удалили и создали заново, пока устройство было офлайн

1. В S1 поправить `Untitled.md` и дождаться синхронизации. Закрыть
   Obsidian на S1.
2. В S2 удалить `Untitled.md`, создать новую `Untitled.md` (Ctrl+N) и
   вписать в неё другой текст. Сервер оживляет тот же `fileId`.
3. Открыть S1. После `connected`: `Untitled.md` на диске S1 и на сервере —
   ровно текст из S2, без строк старой заметки и без повторов. В
   `sync.log` S1 — `warn` «a note’s offline history is not the server’s».
   С сервером, который отдаёт весь журнал (плагин 0.3.8 просит его флагом
   `operationsCatchup`), catch-up показывает удаление и создание заметки
   при любой длине журнала. Прод до исправления сервера (8a6d925) отдаёт
   только первые 500 записей журнала, но историю заметки при оживлении
   заменяет, и S1 видит это по самой истории.
4. Повторить шаги 1–3, но перед закрытием S1 отключить интернет и дописать
   в `Untitled.md` строку, не отправив её. На шаге 3 рядом появляется
   `Untitled.conflict-<ts>.md` с этой строкой, а `Untitled.md` — текст из
   S2. Конфликтная копия уходит на сервер как отдельная заметка. Так с
   любым сервером и при любой длине журнала, по тем же причинам, что в
   шаге 3. Проверить и с заметкой, истории которой на S1 нет: без шага 1,
   в вальте, скопированном на S1 вместе с заметками, или после очистки
   IndexedDB, как после re-seed (заметку на S1 до шага офлайн не открывать и
   не править). С сервером, который отдаёт весь журнал, и с продом в проекте
   с журналом короче 500 операций итог тот же; раньше строка S1 без копии
   вливалась в новую заметку S2 или затирала её текст у всей команды. С
   продом до исправления сервера в более длинном журнале (S1Test2) S1 такую
   заметку от удалённой не отличает, и так остаётся: это снимает выкатка
   сервера.
5. То же с пустой новой заметкой (Ctrl+N без текста): на S1 заметка пустая,
   при любом журнале и любом сервере.
6. Пустая заметка, дописанная с двух сторон: в S1 и S2 есть пустая
   синхронизированная `Todo.md`. S1 офлайн пишет в неё строку, S2 онлайн —
   свою. S1 подключается: в `Todo.md` у всех обе строки, конфликтной копии
   нет.
7. Удаление офлайн заметки, которую коллега удалил и создал заново: S1
   офлайн удаляет `Untitled.md`, S2 удаляет её и создаёт новую
   `Untitled.md` с текстом. S1 подключается: новая заметка S2 остаётся у
   всех и появляется на S1, удаление S1 не уходит (в журнале операций
   сервера нет второго `DELETE`). То же, если S2 не удалял заметку, а
   поправил её: заметка возвращается на S1 с правкой S2.
8. Переименование офлайн заметки, которую коллега удалил и создал заново:
   S1 офлайн переименовывает `Untitled.md` в `Meeting.md`, S2 удаляет
   `Untitled.md` и создаёт новую. S1 подключается: новая заметка S2
   остаётся `Untitled.md` у всех, на S1 нет `Meeting.md`. Если S1 успел
   поправить `Meeting.md`, она уходит на сервер отдельной заметкой. С
   сервером, который отдаёт весь журнал, — при любой его длине. С продом до
   исправления сервера (8a6d925) — только в проекте с журналом короче 500
   операций: в более длинном (S1Test2) catch-up оживления не показывает,
   переименование S1 уходит и у всех переименовывает новую заметку S2 в
   `Meeting.md`. Это снимает выкатка сервера.
9. Переименование в недопустимое имя, пока S1 закрыт: в S2 (0.3.7 или MCP)
   переименовать правленную на S1 заметку в `note.md~`. Если правки S1
   дошли до сервера, при открытии S1 вопроса нет, копия удалена. Если нет —
   вопрос появляется только после `connected`, остальные заметки к этому
   моменту уже синхронизированы.
10. Удаление, пока S1 закрыт: в S2 удалить `a.md` (на S1 есть неотправленная
    правка) и `b.md`. Открыть S1: `b.md` исчезает сразу, вопрос только про
    `a.md`. Пока вопрос открыт, в S2 создать `a.md` заново: на S1 рядом
    появляется `a.conflict-<ts>.md` со старым текстом, `a.md` — текст из S2;
    любой ответ на вопрос оставляет `a.md` как есть.
11. Оживление, которое S1 видел вживую: S1 онлайн, S2 удаляет `Untitled.md`
    и создаёт новую с текстом, на S1 она появляется. Отключить интернет на
    S1 и дописать в `Untitled.md` строку; включить интернет. Строка
    вливается в заметку у всех, конфликтной копии нет. Так же офлайн
    переименование (уходит, у всех одна заметка под новым именем) и офлайн
    удаление (уходит, у S2 заметка исчезает). После перезапуска S1 то же.
12. Правка вложения, которую S1 уже видел вживую: S2 заменяет `image.png`,
    на S1 он обновляется. Отключить интернет на S1, заменить `image.png`
    своим вариантом, включить интернет: на сервере и в S2 — вариант S1,
    вопроса нет.
13. Переименование, которое S1 уже видел вживую: S2 переименовывает `A.md`
    в `B.md`, на S1 она переименована; S1 переименовывает её в `C.md` (или
    обратно в `A.md`) и затем создаёт любую заметку. Pause sync и Resume
    sync: заметка остаётся под именем, которое дал S1, у всех.
14. Новая заметка под именем удалённой: S1 онлайн, `Untitled.md` удалить
    (на S1 или на S2), затем на S1 создать заметку (Ctrl+N) и сразу
    переименовать её в `Meeting.md` (Templater `tp.file.rename` или быстро
    введённый заголовок). У всех одна заметка `Meeting.md`; `Untitled.md`
    нет ни на сервере, ни на диске S1, в том числе после перезапуска S1.
    То же, если сеть на S1 обрывается сразу после Ctrl+N, до ответа
    сервера, а удаление `Untitled.md` S1 видел на одном из прошлых
    подключений: после восстановления связи у всех одна `Meeting.md`, со
    строкой, которую S1 успел дописать без сети. С сервером, который отдаёт
    весь журнал, и с продом.
15. Оживление, пока S1 подключается. Прод до исправления сервера (8a6d925),
    вальт большой, листинг при подключении идёт секунды. Запустить S1 и, пока

### S15 — Пауза и выключение посреди синхронизации

Правка TASK-0030: остановленный движок больше ничего не пишет в вальт и на
сервер, но начатые локальные правки не теряет, а начатое на диске

   синхронизацию на первом. После возобновления на первом устройстве только

   одна не пропала. Операция, бывшая в этот момент «в полёте», может уйти
   второй раз: дубликата на сервере это не создаёт.

   команд нет «Синхронизировать сейчас» и «Приостановить». В DevTools →
   Network соединение с сервером закрыто и не открывается снова, пока идёт
   пауза, хотя сеть есть; новых запросов нет и при правках ниже.
2. На паузе в `test-vault`: переименовать `offlene-a.md` в `chain-b.md`, затем
   в `chain-c.md`; удалить `del.md`; дописать строку в `edit.md`; создать
   `new.md`; создать заметку (Ctrl+N) и сразу переименовать `Untitled.md` в
   `Titled.md`; добавить картинку `pic.png`, заменить `att.png` другой
   картинкой, удалить `old.png`, переименовать `img.png` в `img2.png`. В
   `state.json` в очереди `pending` — эти операции, у `RENAME` и `DELETE`
   непустой `fileId`; в записях файлов уже новые имена, удалённых нет.
3. Тем временем в `test-vault-2` переименовать другую заметку в `chain-b.md`.
4. В `test-vault` «Возобновить синхронизацию»: `connecting` → `syncing` →
   `connected`. У обоих вальтов и на сервере: `chain-c.md` — одна заметка
   `test-vault` под последним именем, `chain-b.md` — заметка `test-vault-2`,
   `offlene-a.md` нет; `del.md` не вернулась; строка в `edit.md` есть;
   `new.md` и `Titled.md` есть, `Untitled.md` нет; картинки как в
   `test-vault`, `old.png` удалена. В журнале операций сервера переименование
   `offlene-a.md` → `chain-c.md` одно, на дисках нет `*.conflict-*`.
5. «Возобновить» и сразу, пока `syncing`, снова «Приостановить», затем
   «Возобновить»: дублей на сервере нет, в `sync.log` нет
   `offline queue drain halted`. Операция, бывшая «в полёте» в момент паузы,
   может уйти второй раз, дубликата это не создаёт. Последнее переименование,
   отправленное до паузы, если сервер его уже применил, второй раз не уходит
   (в `sync.log` —
   `a rename sent from here reached the server before its answer was lost`):
   если `test-vault-2` тем временем переименовал ту же заметку, у всех
   остаётся его имя. Так же с заметкой, переименованной дважды подряд до
   ответа на первое переименование. Ограничение: если на лету были
   переименования нескольких заметок (например, несколько заметок перенесены
   в папку), узнаётся только последнее, остальные уходят второй раз, и
   заметка, которую `test-vault-2` тем временем переименовал, у всех
   возвращается к имени из `test-vault`. Большая картинка, заменённая перед
   паузой, пока идёт её выгрузка: выгрузка обрывается, после возобновления
   картинка уходит один раз. Картинка, которую сервер успел принять, а ответ
   оборвала пауза, и заменённая на паузе ещё раз: после возобновления уходит
   последняя версия, вопроса «Content conflict» нет. Ответ на операцию до
   паузы пришёл — она не мешает сделанному на паузе. Без паузы в
   `test-vault` переименовать заметку в `back.md` (последняя файловая
   операция `test-vault`), в `test-vault-2` переименовать её дальше, на паузе
   в `test-vault` вернуть имя `back.md`, «Возобновить»: у всех `back.md`. Без
   паузы заменить в `test-vault` картинку, в `test-vault-2` заменить её ещё
   раз, на паузе в `test-vault` отредактировать то, что пришло,
   «Возобновить»: у всех правка `test-vault`, вопроса «Content conflict» нет.
   То же с обрывом сети вместо паузы. И с выходом вместо паузы: в
   `test-vault` заменить картинку (или сохранить холст `.canvas`) и выйти из
   Obsidian (или снять его процесс) в первую секунду после того, как новая
   версия ушла на сервер; в `test-vault-2` заменить её ещё раз; снова открыть
   `test-vault`: вопроса «Content conflict» нет, у всех версия
   `test-vault-2`.
6. Новый файл коллеги под тем же именем. Пока `test-vault` на паузе, в
   `test-vault-2` создать заметку (Ctrl+N — `Untitled.md`) с текстом и
   добавить `photo.png`. В `test-vault` «Возобновить» и, пока `syncing` и их
   ещё нет на диске, снова «Приостановить» (на маленьком вальте окно
   короткое: DevTools → Network → Slow 3G). На паузе в `test-vault` создать
   свою `Untitled.md` (Ctrl+N) с другим текстом и положить другую
   `photo.png`, затем «Возобновить». У обоих вальтов и на сервере:
   `Untitled.md` и `photo.png` — файлы `test-vault-2` с их содержимым,
   рядом `Untitled.conflict-<id>.md` и `photo.conflict-<id>.png` — файлы
   `test-vault`; ни один текст и ни одна картинка не пропали. То же, если
   вместо паузы в этот момент выключить сеть или перезапустить Obsidian без
   сети. Обратная проверка: выйти из Obsidian (или снять его процесс) сразу
   после того, как новые файлы `test-vault-2` легли на диск `test-vault`, в
   `test-vault-2` отредактировать один и удалить другой, снова открыть
   `test-vault`. У всех правка на месте, удалённый не вернулся, `*.conflict-*`
   нет (в `sync.log` может быть
   `a file recorded as not written here is on disk; taken for its copy`).
   Перед «Возобновить» в `test-vault` не править `Untitled.md` в
   `test-vault-2` хотя бы 5 секунд. Хэш заметки в списке файлов сервер
   обновляет через 5 секунд после её последней правки. Если заметку правили
   позже, после быстрого выхода её текст на диске `test-vault` не совпадёт
   ни с одним хэшем из списка, и заметку коллеги примут за свою копию.
   Отредактированная коллегой, она даст у всех `Untitled.conflict-<id>.md`
   со старым текстом, удалённая — вернётся у всех. Это ограничение 0.3.8.
7. Выключить привязку в «Хранилища» (Vaults) на паузе и включить снова: status
   bar — `paused`, правка на паузе записывается и уходит после
   «Возобновить». Удалить привязку на паузе: её очередь и офлайн-история
   удаляются, как без паузы.
8. На паузе выключить плагин (Community plugins) и включить снова, или
   перезапустить Obsidian: пауза не сохраняется, плагин подключается сам и
   отправляет изменения, сделанные на паузе.
9. Для сравнения, не на паузе: при закрытом Obsidian переименовать заметку и
   картинку в проводнике (Finder). После запуска у всех две заметки — под
   старым и под новым именем; картинка у `test-vault-2` и на сервере — под
   обоими именами, в `test-vault` — только под новым. То же, если
   переименовать их в Obsidian при выключенной привязке и затем включить её.
   Так и должно быть (README, Limitations): переименовывать и удалять в
   Obsidian, а для работы без синхронизации — пауза.

### S16 — Имена, которые Windows не хранит

Правка из `[Unreleased]`: такие заметки не синхронизируются ни на одной
системе, а уведомления о них точны и не идут шквалом. Шаг 1 — на любой ОС,
шаги 2–6 — на macOS или Linux (Obsidian на Windows сам не даёт создать такие
имена), шаги 7 и 8 — на Windows.

1. Создать заметку `Notes~2.md` так, чтобы она сразу получила это имя:
   щёлкнуть в заметке по неразрешённой ссылке `[[Notes~2]]` или создать файл
   вне Obsidian (Проводник, Finder, `touch`). Примерно через секунду
   появляется уведомление «Team Vault не синхронизирует «Notes~2.md»: имя
   похоже на короткое имя Windows (вроде NOTES~1). На Windows такое имя
   может открыть другой файл…» (English: "…On Windows such a name can open a
   different file…"). Фразы «Windows не может сохранить такое имя» в нём
   нет. В уведомлении есть два совета: заметку, которую уже синхронизировала
   старая версия, переименовать в веб-интерфейсе проекта или через MCP, а
   если её там уже переименовали — перенести правки в переименованную и
   удалить эту копию. На второе устройство заметка не приходит. В `sync.log`
   — `[warn]` с `"problem":"short-name"` и текстом
   `not synced: Windows cannot keep this name as spelled`. Если же создать
   заметку через «Новая заметка» (Ctrl+N) и ввести заголовок `Notes~3`,
   Obsidian сначала создаёт `Без названия.md` (`Untitled.md`) и сразу
   переименовывает её. Тогда приходит другой вариант уведомления: «…Для
   коллег это переименование выглядит как удаление. Переименуйте ещё раз…»,
   без советов про веб-интерфейс, а на втором устройстве `Без названия.md`
   может ненадолго появиться. Это ожидаемо, а не баг.
2. При открытом Obsidian создать вне его (Finder, `touch` в терминале)
   папку `FAQ` с пятью заметками `Question 1?.md` … `Question 5?.md`.
   Появляется одно уведомление «Team Vault не синхронизирует заметки с
   именами, которые не подходят для Windows (имён: 5), например …», а не
   пять. В `sync.log` — пять строк `[warn]`, по одной на заметку. Если
   создавать такие заметки по одной, несколько раз в секунду, в течение
   минуты: уведомления идут не чаще раза в 15 секунд. Каждое следующее
   появляется через 15 секунд после предыдущего, примерно тогда, когда то
   исчезает само. Пауза не зависит от того, видно ли предыдущее: пока над
   ним курсор, Obsidian его не скрывает, и следующее встаёт рядом, а
   закрытое щелчком не приближает следующее.
3. Переименовать в Obsidian папку `FAQ` в `FAQ 2026`, затем перенести
   `Question 1?.md` в другую папку: новых уведомлений и строк в `sync.log`
   нет, на второе устройство ничего не уходит.
4. Создать в Obsidian папку `U.S.` и заметку в ней: уведомление про «U.S.»
   говорит о папке, а не о заметке: «…Переименуйте папку, чтобы
   синхронизировать её заметки с командой…». В нём есть совет для заметок,
   которые в этой папке синхронизировала старая версия: переименовать папку
   или эти заметки в веб-интерфейсе проекта или через MCP, а оставшуюся
   копию, перенеся из неё правки, удалить. Есть и предупреждение, что на
   Windows такое имя нельзя удалять в Проводнике и в системную корзину.
   Фразы «для коллег это переименование выглядит как удаление» в нём нет.
   Перетащить в `U.S.` синхронизированную заметку: приходит второе
   уведомление (не раньше чем через 15 секунд после первого), «…для коллег
   это переименование выглядит как удаление…» с советом переименовать в
   веб-интерфейсе проекта или через MCP заметки, которые в папке с таким
   именем синхронизировала старая версия. На втором устройстве заметка
   удаляется. Дождавшись этого уведомления, перетащить в `U.S.` вторую
   синхронизированную заметку: снова предупреждение об удалении, тоже не
   раньше чем через 15 секунд после предыдущего. Если перетащить обе, пока
   второе уведомление ещё не показано, предупреждение о них будет одно. В
   `sync.log` — строка `[warn]` на каждую перенесённую заметку, с
   `renamedFrom`. Вернуть обе из `U.S.` обратно: они снова синхронизируются
   и появляются на втором устройстве.
5. Переименовать `Question 2?.md` в `Question 2??.md`: уведомление
   приходит (имя сменилось, но осталось плохим). Дождаться, пока оно
   исчезнет само (около 15 секунд). Переименовать синхронизированную
   заметку `Plan.md` в `Plan?.md` и дождаться предупреждения «…для коллег
   это переименование выглядит как удаление…». Затем переименовать её
   обратно в `Plan.md` и снова в `Plan?.md`: предупреждение приходит второй
   раз, не раньше чем через 15 секунд после первого. В `sync.log` — две
   строки `[warn]` с `"renamedFrom":"Plan.md"`. На втором устройстве
   `Plan.md` удаляется, появляется снова и снова удаляется. Без ожидания
   переименования, сделанные, пока уведомление ждёт показа (до 15 секунд
   после предыдущего), делят одно уведомление: три переименования `Plan`
   сразу после `Question 2??.md` дают одно предупреждение, а строк в
   `sync.log` всё равно две.
6. Если в проекте есть заметка вроде `Why?.md`, загруженная старой версией
   плагина, и она лежит на двух устройствах с этой версией: переименовать её
   в веб-интерфейсе проекта в `Why.md`. На обоих устройствах появляется
   `Why.md` с историей, а `Why?.md` остаётся рядом и не синхронизируется,
   как и написано в README («What is never synced»). Правка `Why?.md` даёт
   уведомление с советом перенести правки в переименованную заметку и
   удалить копию. Удалить её вручную.
7. То же на Windows с коротким именем: заметка `Draft~1.md`, загруженная
   старой версией, лежит на устройстве Windows с этой версией. После
   переименования в веб-интерфейсе в `Draft 1.md` рядом с ней остаётся
   несинхронизируемая `Draft~1.md`; её правка даёт уведомление из шага 1.
   Удалить её вручную.
8. То же на Windows с папкой `Notes.`, которую старая версия (0.3.7 или
   раньше) получила с Mac и записала на устройстве Windows под этим именем.
   Проверять на тестовом проекте: ошибка здесь удаляет папку у всей команды.
   Обновить плагин, переименовать `Notes.` в веб-интерфейсе в `Notes`: на
   устройстве Windows появляется `Notes`, а `Notes.` остаётся рядом. Правка
   заметки в `Notes.` даёт уведомление «…имя оканчивается точкой или
   пробелом… Переименуйте папку…» с предупреждением: на Windows не удалять
   такое имя в Проводнике и в системную корзину. Удалить `Notes.`
   безопасным способом из README: в Obsidian, выбрав в «Настройки → Файлы
   и ссылки → Удалённые файлы» вариант «Перемещать в корзину Obsidian
   (папка .trash)» или «Удалять безвозвратно», либо командой
   `rd /s "\\?\<полный путь к хранилищу>\Notes."`. Папка `Notes` со всеми
   заметками остаётся на месте и на этом устройстве, и на втором.

## When done

Заполнить чек-лист (галочки рядом с каждым S1-S16). Найденные баги
фиксить как issues или сразу патчить + добавлять regression-тесты в
`tests/`.

После прохода S1–S10 и S12–S16 (S11 — желательно, но не блокирует; в S16 —
шаги, доступные на ваших системах) можно
выпускать релиз по [RELEASING.md](./RELEASING.md): тег — ровно версия из
`manifest.json`, без `v` (`X.Y.Z`); тег `vX.Y.Z`, который оставляет
`pnpm version`, не пушить.
